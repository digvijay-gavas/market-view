# ARC-0002: Holdings collection in existing Chrome profiles

Status: Implemented; user installation, pairing and live account capture are setup steps.
Date: 2026-11-23.

## Decision

The extension lane runs the holdings parser in the user's ordinary Chrome profile.
This avoids automating Google sign-in. It coexists with the prior browser lane,
while extension pairing switches the local configuration to extension collection.
The price lane and shared dashboard calculation remain in the Node worker.

## Pairing and request flow

The authenticated local admin creates an account-specific ten-minute code. The
extension exchanges it once, then the user confirms the account/profile binding.
An account has one active pairing. The bridge authenticates its token hash,
per-profile client ID and Chrome extension ID on every request. Revocation removes
that credential. Status APIs expose readiness and capture times, not tokens or PINs.

An eligible poll issues a short-lived nonce. The extension opens its own inactive
Groww holdings tab, reads only the required DOM, unlocks a recognised PIN form if
needed, waits for a stable table, and sends structured rows. Login/OTP challenges
stop capture. Empty holdings require positive stable evidence. The tab is closed
in a finally block, and existing user tabs are not closed. The shared parser lives
in `extension/holdings.js`; the legacy browser adapter imports it too.

PIN release is scoped to the current nonce and guarded durably before response.
It is not returned by polling, status or pairing and is never put in extension
storage. The extension keeps only its pair token, client ID and non-financial
capture status in Chrome local storage. No cookie API permission is requested.

The bridge checks complete captures, duplicate instruments, source times and
replay, then saves an encrypted inbox under the same process lock as the worker.
The worker publishes the original capture time and keeps older valid baselines
when no current extension capture is available. Accepted captures can trigger a
worker run after the inbox lock is released. Task Scheduler also keeps the bridge
available for minute polls and continues the shared quote cadence.

## Operational boundaries

- User installation and Google authentication occur in ordinary Chrome. The admin
  can open a known original profile's Extensions page without debugging flags.
- The extension needs that profile running and the computer awake. There is no
  promise of headless operation, missed historical trades or historical quotes.
- Chrome host permissions cover Groww and loopback. Bridge endpoints reject web
  origins, validate extension IDs and require account-scoped credentials. The
  ordinary admin API retains its separate cookie/origin protection.
- Pairing codes and credentials are runtime-only. Neither extension nor private
  runtime state is included in the allowlisted GitHub Pages artifact.
- An extension capture can succeed before Drive setup. Its encrypted inbox remains
  available; Google offline consent/editor access is required for publication.
- Pairing credentials are installation-specific. Moving computers requires a new
  extension installation and pairing in each profile.

## Reconciliation status

The encrypted extension record carries an operation ID, phase and timestamps.
Admin requests create a bounded queued phase. An authenticated extension poll
links that operation to a capture nonce and starts the running phase. Validation
accepts the capture locally before a separate worker publication step. Only a
matching capture nonce plus successful cache compilation marks the operation
succeeded; a newer queued request cannot inherit an older capture's success.
Drive failures retain the inbox and record the failed publication stage.

Admin status projects safe operation metadata and derives expired queue/capture
deadlines. It never exposes capture nonces, tokens or holdings through this
projection. The UI uses that durable state for each account's inline spinner and
caption. Global fetch jobs expose a sanitized result summary, while the worker
persists its last summary so partial runs remain identifiable across restarts.
Lifecycle tests cover deduplication, deadlines, publication failures, nonce
correlation, partial results and browser feedback after reload.

## Managed Chrome lifecycle (2026-11-23)

Admin Reconcile positions, Reconcile all and Fetch now use `managedRun`.
The Windows task calls the same coordinator through `cli scheduled`.

```text
Admin button / Windows task
             |
             v
managedRun -- managed.lock (one collection batch)
             |
             +-- daily/every-run cadence, calendar and interval gate
             |
             v
ordinary Chrome --profile-directory --new-window --start-minimized
             |
             v
127.0.0.1:5186/runner#short-lived-ticket
             | extension content script (this path only)
             v
account-scoped extension worker -- paired token --> ExtensionBridge
             |
             v
temporary Groww tab IN collector window
             |
             +--> validated encrypted capture inbox
             +--> close owned tab/window; preserve other tabs
             |
             v
Node worker -- run.lock --> positions + shared prices + ONE cache build
             |
             v
private sync-history.json (last 12 attempts; no holdings or credentials)
```

The local runner page is public only on loopback and contains no credentials.
Its random ticket is not sufficient to read a PIN or submit a capture: the
extension still authenticates with its existing per-profile token, client ID and
extension ID. Other alarm polls cannot consume a managed request. Expired runner
tickets cannot create another capture after the coordinator has finished.

The extension removes its old polling alarm. Automatic prices obey the configured
5-240 minute interval with up to one minute of jitter, during verified NSE hours.
Positions default to once per market day; the UI also permits every update.
Missed position days are detected from the last published position timestamp.
Authentication/PIN failures retain the existing retry and one-attempt guards.

The coordinator releases the publication lock while Chrome is working. It visits
profiles sequentially, waits up to 210 seconds per account, records failures, then
refreshes prices/cache once from available complete baselines. Only successful
publication marks a capture reconciled. Failed or partial captures retain old
data. History distinguishes capture failure from a partially refreshed cache.

Windows created for collection close after capture. If someone adds a tab to the
collection window, cleanup closes only collector tabs. Chrome background processes
and pre-existing windows are never forcibly terminated. Initial login/OTP remains
interactive when required. Unpacked installations need one extension reload after
this update; stored pairing and signed-in Chrome profiles remain in place.

Verification: focused coordinator tests cover due gates, serialization, failed
launches, ticket scope and cleanup ownership. The unpacked MV3 integration test
captures synthetic holdings and verifies the owned window closes while its
separate popup remains open. Mobile admin tests cover rendering and durable
per-button progress. No live-account success is implied by synthetic tests.
