# ARC-0002: Holdings collection in existing Chrome profiles

Status: Implemented; user installation, pairing and live account capture are setup steps.
Date: 2026-11-23.

## Decision

The extension lane runs the holdings parser in the user's ordinary Chrome profile.
This avoids automating Google sign-in. It coexists with the prior browser lane,
while extension pairing switches the local configuration to extension collection.
The price lane and shared dashboard calculation remain in the Node worker.

## Pairing and request flow

The authenticated local admin creates an account-specific ten-minute code. The
extension exchanges it once, then the user confirms the account/profile binding.
An account has one active pairing. The bridge authenticates its token hash,
per-profile client ID and Chrome extension ID on every request. Revocation removes
that credential. Status APIs expose readiness and capture times, not tokens or PINs.

An eligible poll issues a short-lived nonce. The extension opens its own inactive
Groww holdings tab, reads only the required DOM, unlocks a recognised PIN form if
needed, waits for a stable table, and sends structured rows. Login/OTP challenges
stop capture. Empty holdings require positive stable evidence. The tab is closed
in a finally block, and existing user tabs are not closed. The shared parser lives
in `extension/holdings.js`; the legacy browser adapter imports it too.

PIN release is scoped to the current nonce and guarded durably before response.
It is not returned by polling, status or pairing and is never put in extension
storage. The extension keeps only its pair token, client ID and non-financial
capture status in Chrome local storage. No cookie API permission is requested.

The bridge checks complete captures, duplicate instruments, source times and
replay, then saves an encrypted inbox under the same process lock as the worker.
The worker publishes the original capture time and keeps older valid baselines
when no current extension capture is available. Accepted captures can trigger a
worker run after the inbox lock is released. Task Scheduler also keeps the bridge
available for minute polls and continues the shared quote cadence.

## Operational boundaries

- User installation and Google authentication occur in ordinary Chrome. The admin
  can open a known original profile's Extensions page without debugging flags.
- The extension needs that profile running and the computer awake. There is no
  promise of headless operation, missed historical trades or historical quotes.
- Chrome host permissions cover Groww and loopback. Bridge endpoints reject web
  origins, validate extension IDs and require account-scoped credentials. The
  ordinary admin API retains its separate cookie/origin protection.
- Pairing codes and credentials are runtime-only. Neither extension nor private
  runtime state is included in the allowlisted GitHub Pages artifact.
- An extension capture can succeed before Drive setup. Its encrypted inbox remains
  available; Google offline consent/editor access is required for publication.
- Pairing credentials are installation-specific. Moving computers requires a new
  extension installation and pairing in each profile.

## Verification

Unit tests exercise one-time pairing, expiry/revocation, account and client
isolation, market-day cadence, PIN guards, stale data, empty/partial rows and replay.
The MV3 integration test loads the real extension in disposable Chromium, pairs
through the HTTP bridge, and collects a mocked Groww holdings page. It uses no
real account cookies or PINs. CI enables this test explicitly.
